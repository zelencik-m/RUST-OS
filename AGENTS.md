# AGENTS.md

`no_std` x86_64 hobby kernel (blog_os lineage, `bootloader` 0.9 + `bootimage`). See `README.md` for scheduler/process design notes.

## Toolchain & commands
- Nightly Rust required (uses `build-std`, `json-target-spec`, custom target `x86_64-blog_os.json`, set as the default target in `.cargo/config.toml`). The nightly is pinned in `rust-toolchain.toml` (with `rust-src` and `llvm-tools-preview`); bump it deliberately.
- External tools: `bootimage` (cargo runner), `qemu-system-x86_64`, `clang` (used by `build.rs`), and `rust-lld` from the Rust sysroot.
- Quick compile check: `cargo check` (also `cargo check --tests`).
- All tests: `cargo test`. One suite: `cargo test --test <file_stem>` (e.g. `userspace`, `filesystem`, `heap`). Each suite boots its own QEMU (timeout 300s); success = isa-debug-exit code 33.
- `cargo run` boots the kernel in QEMU into the shell (`/bin/sh`) and **never exits**. Don't run it in the foreground. To drive it headless, add `-- -display none -monitor tcp:127.0.0.1:PORT,server,nowait` and type with the monitor's `sendkey`; shell output is mirrored to serial, and `screendump` captures the VGA screen.
- There are no unit tests: `[lib]` and `[[bin]]` have `test = false`. Every test is a `#![no_std]` integration target in `tests/` using `custom_test_frameworks` + `#[test_case]` and `tests/support/mod.rs` (`mod support;`).

## User programs (C → ELF)
- `build.rs` compiles C programs with clang and links them with `user_programs/linker.ld` into `$OUT_DIR/<name>.elf`. The kernel and tests embed them with `include_bytes!(concat!(env!("OUT_DIR"), ...))`.
- To add a program, add it to `PROGRAMS` in `build.rs` **and** embed it where it's used (`src/main.rs`, `tests/userspace.rs`, `tests/elf_images.rs`). The `userspace` runner expects exactly one `#[test_case]` and keys success off per-program output markers (`add_case_with_argv` starts a case with an argv).
- Each `PROGRAMS` entry has a link kind. `Ulib` programs define `main` and get `user_programs/ulib` (crt0 `_start`, syscall wrappers, string/mem functions, printf; see `ulib.h`). Wrappers return `-errno`, there is no `errno`. `Bare` programs (the older tests, `thread_b`/`thread_c`) define their own `_start` and must not be linked with crt0. Prefer `Ulib` for new programs: without ulib's `memcpy`/`memset`, a struct copy or array initializer fails to link.
- `src/main.rs` installs its embedded programs into `/bin` on the ext2 disk at every boot (`rust_os::programs::install`, O_TRUNC rewrite). `programs::load` reads a program file back (used by `spawn`). Test kernels don't install anything; `userspace` puts what it needs into its RamFs `/bin`.
- Syscall numbers live only in `src/syscall/numbers.rs` (Linux numbering plus custom ones from 1000: `SYS_SLEEP_TICKS`, `SYS_TTY_MODE`, `SYS_SPAWN`, `SYS_TTY_FOREGROUND`). `build.rs` generates `$OUT_DIR/syscall_numbers.h` from it (lines of the form `pub const SYS_X: u64 = N;`), which `user_programs/syscalls.h` includes.
- C code must stay freestanding (no SSE, no red zone, large code model). User programs load at `0x00007F8000100000` (P4 slot 255).

## Runtime gotchas
- `rust_os::init` mounts `ext2.img` (committed to git, 32 MiB) as the VFS root over ATA PIO, secondary master (`-drive ... index=2` in `Cargo.toml` bootimage args). A missing or corrupt image panics boot. QEMU never boots the committed image: the cargo runner `scripts/qemu-runner.sh` stages `target/ext2-disk.img` (fresh copy for every test suite; kept between `cargo run`s, delete it to reset), and the bootimage args point at that copy.
- The `userspace` and `filesystem` tests run against an in-memory `RamFs`, not ext2 contents. They still call `init`, so the image still has to mount.
- Lock order is always **TTY → SCHEDULER → PROCESS_MANAGER → MEMORY_MANAGER** (`src/process/process_manager/api.rs`; the keyboard IRQ wakes readers with the TTY lock taken first). Drop locks before `switch_context`.
- Block with `WaitQueue::wait_until` (`src/scheduler/wait_queue.rs`), never while holding an `IrqSafeMutex`: it panics if interrupts are off. Device reads in `sys_read` release PROCESS_MANAGER before calling into the device for this reason.
- The heap allocator's lock (`Locked`, `src/memory/allocator.rs`) disables interrupts, so interrupt handlers may allocate and free (the timer's reaper and process exit do). Keep the keyboard path allocation-free anyway: the TTY uses fixed-size rings, and the run queue reserves capacity at boot.
- Never write `if let Some(x) = LOCK.lock().get()` before code that takes the same lock: the guard (a temporary in the scrutinee) lives until the end of the block. Bind the value with `let` first.
- Processes: `spawn_process` / `wait_child` / `request_kill` in `src/process/process_manager/api.rs`. Every user thread starts with an argc/argv stack (`initial_stack.rs`); `spawn_elf` is `spawn_process` with argv `[name]` and console stdio. A Ctrl-C kill only sets `pending_kill`; the process exits itself in `exit_if_killed` at a safe point (end of a syscall, or a timer tick that interrupted ring 3).
- Kernel thread stacks are 16 KiB with no guard page. An overflow corrupts memory silently (often a jump to address 0). Build large state in `static`s with `const fn` constructors, not with `lazy_static`, which builds the value on the stack.
- Kernel log (`src/debug/`, serial only): `log_error!`/`log_warn!`/`log_info!`/`log_debug!`/`log_trace!`, filtered by `debug::set_level`. A normal boot uses `LOG_LEVEL` in `src/main.rs` (`Info`). Use `trace` for anything per context switch, sleep or syscall; `info` only for milestones. Test kernels keep logging off, and `basic_boot` asserts that. Logging is called with locks held (even SCHEDULER), so it must never take a lock other than its serial port: timestamps come from an atomic tick counter.
- Boot: `src/main.rs` installs `sh`, `hello`, `thread_b`, `thread_c` into `/bin`, then a kernel thread (`shell_supervisor`) loads `/bin/sh` from disk, spawns it (parent PID 0, console stdio) and starts a new one whenever it exits.
- The shell (`user_programs/sh.c`) switches the console to raw mode and edits lines itself; around each program it switches to cooked mode and makes the child the Ctrl-C target. With a non-console stdin (`tty_mode` fails with ENOTTY) it runs in script mode, which is what `tests/userspace.rs` uses (`sh_script`; `sh_interactive` types keys instead). Runner cases can require several output markers in order and send stderr into stdout (`add_case_with` + `CaseStdio`).
- Output goes to the VGA buffer (`println!`) and to serial (`serial_println!`, which QEMU sends to stdio). Test results are read from serial. The VGA writer (`src/vga_buffer.rs`) is a small terminal: text fills downward from the top and scrolls at the bottom; `\r`, `\t`, `\x08` (move left, no erase), `\x0c` (clear); ANSI `m` (colors), `J`, `K`, `H`, `A`–`D`; UTF-8 mapped to CP437 by `vga_buffer::cp437` (unknown → ■). `set_scroll_top` reserves rows above the text area (the status bar on row 0); `draw`/`fill` paint fixed cells with raw CP437 bytes.
- Look: `src/theme.rs` has two palettes, loaded into the VGA DAC with `theme::load(palette, level)` (level 0–16 scales brightness; blinking is turned off so backgrounds 8–15 are bright). `BOOT` is a 14-step gradient (`theme::shade(n)`) plus amber and glow; `TERMINAL` is the console's (ANSI colors land on its slots; magenta/pink are dark gradient shades). Kernel UI uses the role names in `src/theme.rs`. Boot: `boot_screen::begin`, `init_with` reports each step via `boot_screen::step` (no allocation: it runs before the heap), then `shell_supervisor` plays `boot_screen::animate`, clears, loads `TERMINAL` (`theme::apply`), installs the status bar (`status_bar::install` + its refresh thread) and starts the shell. Screens are checked by booting headless and taking QEMU `screendump`s.
- Console output (`write` to fd 1/2, TTY echo) goes to VGA and serial as raw bytes (`vga_buffer::write_bytes`, `serial::write_bytes`), never through `&str`: a write can end mid-UTF-8 character, and both outputs decode across writes.
- Keyboard: IRQ → `keyboard::handle_scancode` → `tty::push_key`. `tests/tty_blocking.rs` and the userspace runner's `input` hook type keys by calling `tty::push_key` directly.
